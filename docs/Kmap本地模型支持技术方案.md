# Kmap项目本地模型支持技术实现方案

## 一、现有架构分析
Kmap项目采用典型的前后端分离架构：
- **后端**：Python FastAPI框架，通过LLMFactory和EmbeddingFactory抽象层支持多服务商LLM/Embedding接入，当前代码已接入OpenAI、Claude（火山方舟兼容）、Gemini、自定义OpenAI兼容接口
- **前端**：React单页应用，通过统一的API服务层调用后端接口，已实现服务拆分（chatService、graphService等）
- **移动端**：基于Capacitor的混合开发架构，支持Android平台，已实现原生文件操作、权限管理等桥接能力
- **Android端**：minSdkVersion 支持Android 6.0+，当前使用Capacitor框架桥接Web与原生能力

## 二、模型选型推荐

### 2.1 轻量级Embedding模型选型
| 模型名称 | 参数量 | 模型体积 | 向量维度 | 精度（MTEB） | 推理速度（移动端CPU） | 资源占用 | 适用场景 |
|---------|-------|---------|---------|-------------|----------------------|---------|---------|
| **bge-small-zh-v1.5** | 33M | 65MB | 512 | 62.8 | ~8ms/句 | 内存 < 100MB | 中文场景优先推荐，平衡精度与性能 |
| **bge-micro-v2** | 22M | 44MB | 512 | 59.3 | ~5ms/句 | 内存 < 80MB | 低配置设备场景 |
| **all-MiniLM-L6-v2** | 22M | 43MB | 384 | 58.8 | ~5ms/句 | 内存 < 70MB | 英文/多语言场景 |
| **gte-tiny** | 16M | 32MB | 768 | 57.9 | ~4ms/句 | 内存 < 60MB | 极致性能要求场景 |

**推荐选型**：优先选择`bge-small-zh-v1.5`作为中文场景主力模型，`bge-micro-v2`作为低配设备备选。

### 2.2 小语言模型选型
| 模型名称 | 参数量 | 模型体积（FP16） | 量化后体积（INT4） | 上下文窗口 | 推理速度（移动端） | 精度（MMLU） | 资源占用 | 适用场景 |
|---------|-------|-----------------|-------------------|-----------|-------------------|-------------|---------|---------|
| **Qwen-1.8B-Chat** | 1.8B | 3.6GB | 450MB | 8k | ~8 tokens/s | 48.3 | 内存 < 1GB | 综合能力优先，支持复杂对话 |
| **Phi-2** | 2.7B | 5.4GB | 680MB | 2k | ~6 tokens/s | 56.7 | 内存 < 1.5GB | 高性能设备，复杂推理场景 |
| **Gemini-Nano-2** | 3.2B | - | 800MB | 32k | ~5 tokens/s | 55.4 | 内存 < 1.8GB | Google生态设备优先 |
| **Llama-3-8B-Instruct** | 8B | 16GB | 2GB | 8k | ~3 tokens/s | 68.2 | 内存 < 3GB | 高端设备，专业场景 |
| **MiniCPM-2B-sft** | 2B | 4GB | 500MB | 8k | ~7 tokens/s | 51.2 | 内存 < 1.2GB | 中文场景优化 |

**推荐选型**：
- 主力模型：`Qwen-1.8B-Chat`（INT4量化），平衡体积、速度和中文能力
- 低配设备备选：`MiniCPM-2B-sft`（INT4量化），针对中文场景优化
- 高端设备可选：`Llama-3-8B-Instruct`（INT4量化），提供更强推理能力

## 三、部署模式对比分析

### 3.1 模式1：端侧直接运行模型推理
**架构说明**：模型完全运行在用户设备（PC/移动端）上，推理过程完全本地完成，无需网络连接。

**优势**：
- ✅ 数据完全本地化，隐私安全性最高
- ✅ 无需搭建后端服务，部署简单
- ✅ 响应速度不受网络影响
- ❌ 设备性能要求高，低端设备运行困难
- ❌ 模型体积大，首次下载成本高
- ❌ 多设备同步困难
- ❌ 模型更新复杂

**适用场景**：
- 高隐私敏感场景（涉密文档处理）
- 网络受限环境（离线使用需求）
- 高端设备用户群体

### 3.2 模式2：本地轻量化后端服务部署
**架构说明**：用户在本地PC或局域网设备部署轻量化后端服务，模型运行在本地服务端，前端通过本地API调用。

**优势**：
- ✅ 可利用PC/服务器更强算力，运行更大模型
- ✅ 多设备可共享同一模型服务
- ✅ 模型更新、管理更便捷
- ✅ 降低移动端设备性能要求
- ❌ 需要用户自行部署维护服务
- ❌ 局域网环境要求
- ❌ 部署复杂度较高

**适用场景**：
- 企业内部部署场景
- 多设备协同使用场景
- 需要运行大模型的专业用户
- 已有本地服务器资源的用户

### 3.3 推荐部署策略
采用**混合部署模式**作为最终方案：
1. 移动端默认采用模式1（端侧推理），支持离线使用
2. PC端同时支持两种模式，用户可自由选择
3. 企业用户推荐模式2，提供集中管理能力

## 四、云/本地模型兼容方案设计

### 4.1 架构设计
```
┌─────────────────────────────────────────────────────────┐
│                     前端应用层                           │
├─────────────────────────────────────────────────────────┤
│                   模型调度管理层                         │
│  ┌─────────────┐  ┌─────────────┐  ┌─────────────┐     │
│  │ 路由策略引擎 │  │ 健康检查模块 │  │ 降级处理模块 │     │
│  └─────────────┘  └─────────────┘  └─────────────┘     │
├─────────────────────────────────────────────────────────┤
│                   模型实现适配层                         │
│  ┌─────────────┐  ┌─────────────┐  ┌─────────────┐     │
│  │  云服务适配  │  │ 端侧推理适配 │  │ 本地服务适配 │     │
│  └─────────────┘  └─────────────┘  └─────────────┘     │
└─────────────────────────────────────────────────────────┘
```

### 4.2 自动切换策略
1. **优先级策略**：用户可配置模型优先级（本地优先/云端优先）
2. **健康检测机制**：
   - 本地模型启动时自动检测可用性
   - 每次推理前检查模型状态
   - 推理失败时自动重试2次
3. **降级规则**：
   - 本地模型不可用时自动切换到云端
   - 云端不可用时提示用户检查网络或配置
   - 支持手动切换模式
4. **兼容设计**：
   - 保持现有API接口不变，后端透明处理模型切换
   - 前端无需感知后端模型类型，统一调用接口
   - 新增模型管理界面，支持用户下载、删除、配置本地模型

### 4.3 后端兼容方案
在现有`LLMFactory`和`EmbeddingFactory`基础上扩展：
1. 新增`local`类型的provider支持
2. 实现本地模型推理引擎，调用端侧或本地服务接口
3. 保持现有`LLMService`和`EmbeddingService`接口不变
4. 新增模型管理API，支持模型上传、下载、状态查询等操作

## 五、安卓端侧部署方案

### 5.1 推理框架选型
| 框架 | 支持模型格式 | 硬件加速 | 性能表现 | 集成难度 | 推荐指数 |
|------|-------------|---------|---------|---------|---------|
| **ONNX Runtime Mobile** | ONNX | CPU/GPU/NPU | 优秀 | 中 | ⭐⭐⭐⭐⭐ |
| **TensorFlow Lite** | TFLite | CPU/GPU/NNAPI | 良好 | 低 | ⭐⭐⭐⭐ |
| **MNN** | MNN/ONNX/TFLite | CPU/GPU/NPU | 优秀 | 高 | ⭐⭐⭐ |
| **PyTorch Mobile** | TorchScript | CPU/GPU | 良好 | 中 | ⭐⭐⭐ |

**推荐选型**：优先选择**ONNX Runtime Mobile**，支持丰富的模型格式和硬件加速，生态完善，性能优异。

### 5.2 架构设计
```
┌─────────────────────────────────────────────────────────┐

                    │
┌───────────────────▼─────────────────────────────────────┐
│                  原生推理服务层                         │
│  ┌─────────────┐  ┌─────────────┐  ┌─────────────┐     │
│  │ 模型管理模块 │  │ ONNX Runtime│  │ 性能监控模块 │     │
│  └─────────────┘  └─────────────┘  └─────────────┘     │
└───────────────────┬─────────────────────────────────────┘
                    │

│                     硬件抽象层                          │
│  CPU / GPU / NPU (NNAPI) 硬件加速支持                   │
└─────────────────────────────────────────────────────────┘
```

### 5.3 性能控制策略
1. **内存控制**：
   - 模型加载前检查可用内存，不足时提示用户
   - 推理完成后及时释放中间张量内存
   - 采用内存池技术复用内存资源
2. **CPU/GPU占用控制**：
   - 推理线程数动态适配设备核心数，默认使用n-1个核心
   - 后台运行时自动降低优先级，减少CPU占用
   - 支持用户配置性能模式（性能优先/平衡/省电）
3. **功耗优化**：
   - 批量推理合并，减少硬件唤醒次数
   - 空闲时自动卸载模型，释放资源
   - 低电量模式下自动降低推理性能

## 六、模型优化方案

### 6.1 量化压缩方案
| 量化方式 | 精度损失 | 压缩率 | 推理速度提升 | 适用场景 |
|---------|---------|--------|-------------|---------|
| **INT4 对称量化** | < 5% | 4x | ~2.5x | 优先推荐，平衡精度与性能 |
| **INT8 对称量化** | < 2% | 2x | ~1.5x | 对精度要求高的场景 |
| **FP16 半精度** | < 1% | 2x | ~1.2x | GPU推理场景 |

**优化路径**：
1. 对Embedding模型默认采用INT8量化，体积从65MB压缩到35MB
2. 对LLM模型默认采用INT4量化，体积从3.6GB压缩到450MB
3. 提供不同量化等级的模型供用户选择下载

### 6.2 模型蒸馏方案
针对Kmap特定场景（知识图谱构建、文档问答）进行领域蒸馏：
1. 用云端大模型（如GPT-4、Claude 3）生成领域相关问答对
2. 用生成的数据微调小语言模型，提升特定任务表现
3. 预期在知识问答场景下精度提升15-20%

### 6.3 优化目标
| 指标 | 基线值 | 优化目标 |
|------|-------|---------|
| Embedding模型体积 | 65MB | ≤ 35MB |
| LLM模型体积（1.8B） | 3.6GB | ≤ 500MB |
| Embedding推理延迟 | 8ms/句 | ≤ 5ms/句 |
| LLM推理速度 | 5 tokens/s | ≥ 8 tokens/s |
| 端侧内存占用峰值 | 1.2GB | ≤ 800MB |

## 七、技术风险与实施路线

### 7.1 技术风险评估
| 风险点 | 影响程度 | 发生概率 | 应对方案 |
|-------|---------|---------|---------|
| 端侧模型推理性能不足 | 高 | 中 | 提供多档量化模型，动态适配设备性能 |
| 模型精度损失过大 | 高 | 低 | 充分测试不同量化方案，保留精度备份 |
| Android碎片化兼容性问题 | 中 | 高 | 针对主流芯片（骁龙、联发科）专项优化，建立兼容性测试矩阵 |
| 模型下载体积过大 | 中 | 中 | 采用分块下载、断点续传、压缩传输 |
| 端侧推理框架兼容性问题 | 中 | 中 | 封装抽象层，支持多推理框架 fallback |
