# Kmap项目后端技术栈初步方案
## 项目背景
Kmap是一个知识图谱应用，前端采用React 19 + TypeScript + Vite技术栈，需要支持以下核心功能：
- 文档上传与解析（支持多种格式）
- 知识抽取与结构化处理
- 向量存储与相似性检索
- 图谱查询与关系分析
- AI问答与知识推理
## 1. 后端编程语言和框架选型
### 方案一：Python + FastAPI
**优点：**
- 生态丰富：拥有完善的AI/ML生态系统，适合知识抽取、NLP处理等AI相关功能开发
- 开发效率高：语法简洁，开发速度快，适合快速迭代和原型验证
- FastAPI高性能：异步支持，自动生成API文档，类型提示完善，性能接近Node.js和Go
- 团队熟悉度高：AI相关开发人员对Python生态更为熟悉
**缺点：**
- 运行性能相对较低：CPU密集型任务性能不如Go和Java
- 异步生态不够完善：部分第三方库对异步支持不足
- 部署打包相对复杂：Python依赖管理和打包部署相对麻烦
### 方案二：Go + Gin/Gin-v2
**优点：**
- 性能优异：编译型语言，运行效率高，资源占用低，适合高并发场景
- 部署简单：编译为单一二进制文件，部署极其方便
- 标准库强大：网络编程、并发处理能力强，适合构建高性能API服务
- 静态类型：编译时检查，代码质量更有保障
**缺点：**
- AI生态相对薄弱：知识抽取、NLP相关的库不如Python丰富
- 开发效率略低：语法相对繁琐，开发周期比Python长
- 团队学习成本：如果团队主要熟悉Python，需要一定的学习周期
### 方案三：Java + Spring Boot
**优点：**
- 生态成熟：企业级应用生态非常完善，稳定性高
- 性能优秀：JVM优化成熟，长期运行性能稳定
- 社区资源丰富：问题排查和解决方案多
**缺点：**
- 开发效率低：代码臃肿，部署打包慢，不适合快速迭代
- 内存占用高：资源消耗相对较大
- AI生态支持一般：AI相关工具链不如Python完善
### 初步选型结论：主选Python + FastAPI，关键性能模块使用Go扩展
- 主服务采用Python + FastAPI，快速实现业务逻辑和AI相关功能
- 对于文档解析、高并发查询等性能敏感模块，采用Go开发独立服务，通过GRPC或HTTP接口调用
## 2. 数据库选型
### 2.1 关系型数据库
#### 方案一：PostgreSQL
**优点：**
- 功能强大：支持JSONB、数组、地理信息等丰富的数据类型
- 扩展性好：支持多种扩展，如pgvector（向量存储）、age（图查询）
- ACID兼容：事务支持完善，数据一致性有保障
- 社区活跃：稳定性高，生态成熟
**缺点：**
- 写入性能相对MySQL略低
- 运维复杂度比MySQL略高
#### 方案二：MySQL
**优点：**
- 性能稳定：写入性能优异，适合高并发写入场景
- 运维成熟：团队熟悉度高，运维工具丰富
- 生态完善：各种中间件和工具支持丰富
**缺点：**
- 高级功能支持不足：对向量、图数据等扩展支持不如PostgreSQL
### 初步选型：PostgreSQL
- 主存储采用PostgreSQL，存储用户信息、文档元数据、业务数据等结构化信息
- 利用pgvector扩展直接支持向量存储，减少技术栈复杂度
### 2.2 向量数据库
#### 方案一：pgvector（PostgreSQL扩展）
**优点：**
- 技术栈统一：无需额外部署和维护独立的向量数据库
- 事务支持：向量数据和业务数据可以在同一个事务中操作，保证一致性
- 查询灵活：可以结合SQL进行复杂的混合查询（关系数据 + 向量检索）
**缺点：**
- 大规模向量检索性能不如专业向量数据库
- 高级向量功能支持有限（如多模态、量化等）
#### 方案二：Milvus
**优点：**
- 专业向量数据库：性能优异，支持海量向量数据的高效检索
- 功能丰富：支持多种索引类型、多模态向量、量化压缩等高级功能
- 扩展性好：支持分布式部署，水平扩展能力强
**缺点：**
- 运维复杂度高：需要独立部署和维护，增加系统复杂度
- 数据一致性需要额外处理：和业务数据库分开存储，需要保证数据同步
#### 方案三：Chroma
**优点：**
- 轻量级：部署简单，适合中小规模应用
- Python友好：API简洁，和Python生态集成度高
**缺点：**
- 分布式支持不足：不适合大规模生产环境
- 性能相对较弱：高并发查询性能有限
### 初步选型：短期使用pgvector，中长期考虑Milvus
- 项目初期使用pgvector，减少运维复杂度，满足初期向量检索需求
- 当向量数据量超过1000万条或对检索性能有更高要求时，迁移到Milvus
### 2.3 图数据库
#### 方案一：Neo4j
**优点：**
- 图数据库事实标准：功能强大， Cypher查询语言成熟
- 生态完善：工具链丰富，可视化支持好
- 性能优异：图遍历和关系查询性能高
**缺点：**
- 开源版功能受限：集群、高可用等高级功能需要商业版
- 存储成本高：大数据量下存储成本较高
#### 方案二：Nebula Graph
**优点：**
- 开源分布式：支持水平扩展，适合大规模图数据存储
- 性能优异：高性能图遍历和查询
- 国产开源：中文文档完善，社区活跃
**缺点：**
- 生态相对较小：工具链和第三方集成不如Neo4j丰富
- 学习成本较高：查询语言nGQL需要学习
#### 方案三：PostgreSQL + AGE扩展
**优点：**
- 技术栈统一：基于PostgreSQL，无需额外部署
- 支持OpenCypher查询：兼容标准Cypher语法
- 数据一致性好：和业务数据、向量数据存储在同一个数据库
**缺点：**
- 图查询性能不如专业图数据库
- 功能相对有限：高级图算法支持不足
### 初步选型：短期使用PostgreSQL + AGE，中长期考虑Nebula Graph
- 项目初期使用AGE扩展，快速实现图谱基本功能，减少技术复杂度
- 当图谱节点超过1000万或关系查询性能成为瓶颈时，迁移到Nebula Graph
## 3. 核心中间件和服务选型
### 3.1 文档解析服务
#### 方案一：Unstructured.IO
**优点：**
- 支持格式丰富：支持PDF、Word、PPT、Excel、图片等几乎所有常见文档格式
- 解析能力强：结构化解析效果好，支持表格、图片、公式等元素提取
- 活跃的社区：更新迭代快，功能持续增强
**缺点：**
- 资源消耗高：解析服务对CPU和内存要求较高
- 部署复杂：依赖较多，部署和运维相对复杂
#### 方案二：LangChain + 自定义解析器
**优点：**
- 高度灵活：可以根据需求定制解析逻辑
- 轻量级：按需加载解析器，资源消耗可控
**缺点：**
- 格式支持有限：需要自行实现多种格式的解析
- 开发工作量大：需要投入较多精力开发和优化解析逻辑
### 初步选型：Unstructured.IO作为核心解析服务，自定义解析器作为补充
- 部署Unstructured.IO独立服务，负责通用文档格式解析
- 对于特殊格式或定制化解析需求，开发自定义解析器
### 3.2 消息队列
#### 方案一：RabbitMQ
**优点：**
- 可靠性高：消息持久化、ACK机制完善，适合可靠性要求高的场景
- 路由功能丰富：支持多种消息路由模式
- 管理界面友好：运维方便
**缺点：**
- 吞吐量相对较低：高并发场景下性能不如Kafka
- 堆积能力有限：大量消息堆积时性能下降明显
#### 方案二：Kafka
**优点：**
- 高吞吐量：适合大数据量、高并发场景
- 消息堆积能力强：支持海量消息存储
- 生态完善：和大数据、AI生态集成度高
**缺点：**
- 运维复杂度高：需要部署ZooKeeper或KRaft集群
- 功能相对单一：高级路由功能支持不足
### 初步选型：Kafka
- 用于文档处理、知识抽取等异步任务的消息队列
- 支持高吞吐量和海量消息堆积，适合离线处理场景
### 3.3 缓存服务
#### 方案：Redis
**优点：**
- 性能优异：内存数据库，读写性能极高
- 功能丰富：支持多种数据结构，可用于缓存、会话存储、分布式锁等场景
- 生态成熟：运维工具丰富，团队熟悉度高
**缺点：**
- 内存成本较高：大量数据存储成本较高
### 选型结论：Redis作为统一缓存服务
- 用于热点数据缓存、会话管理、分布式锁、接口限流等场景
### 3.4 AI服务
#### 大模型选型
- 支持多种大模型适配：OpenAI GPT系列、Anthropic Claude系列、国内通义千问、文心一言等
- 采用轻量SDK封装，支持灵活切换不同厂商的大模型服务
#### Embedding模型
- 通用场景：OpenAI text-embedding-3系列、国内BGE系列
- 垂直领域：根据业务需求训练或微调领域专用Embedding模型
## 4. 部署架构方案
### 方案一：单体架构（初期）
**架构设计：**
- 单一FastAPI应用服务，包含所有业务逻辑
- PostgreSQL数据库（集成pgvector + AGE扩展）
- Redis缓存服务
- Unstructured.IO独立解析服务
**优点：**
- 架构简单，部署运维成本低
- 开发效率高，适合快速迭代
- 适合项目初期10万用户以下规模
**缺点：**
- 扩展性有限：业务复杂度提升后难以水平扩展
- 可用性较低：单点故障影响整个服务
### 方案二：微服务架构（中长期）
**架构设计：**
- API网关：统一入口，负责路由、限流、认证等
- 业务微服务：
  - 用户服务：用户管理、权限认证
  - 文档服务：文档上传、解析管理
  - 知识抽取服务：知识结构化处理、实体关系抽取
  - 图谱服务：图谱数据管理、查询分析
  - 向量服务：向量存储、相似性检索
  - AI问答服务：对话管理、prompt工程、大模型调用
- 数据层：
  - PostgreSQL集群：业务数据存储
  - Milvus集群：向量数据存储
  - Nebula Graph集群：图数据存储
  - Redis集群：缓存服务
  - Kafka集群：消息队列
- 基础设施：K8s集群部署，服务网格治理
**优点：**
- 扩展性好：各个服务可以独立水平扩展
- 可用性高：单个服务故障不影响整体服务
- 技术栈灵活：不同服务可以选择最合适的技术栈
**缺点：**
- 架构复杂：运维成本高，需要专业的DevOps团队
- 开发成本高：服务拆分、分布式事务、服务治理等增加开发复杂度
### 部署架构演进路线
1. **V1.0阶段（0-3个月）**：采用单体架构，快速开发上线，验证产品需求
2. **V2.0阶段（3-6个月）**：拆分核心服务，将文档解析、知识抽取、AI问答等独立为服务，逐步向微服务过渡
3. **V3.0阶段（6个月以上）**：全面微服务架构，基于K8s部署，支持大规模用户访问
