# Kmap项目后端技术栈选型报告
## 版本信息
- 版本：v1.0
- 日期：2026-03-08
- 状态：最终版
## 需求适配评估
本次选型基于最新产品需求，对初步方案进行评估和优化，重点覆盖以下核心需求：
1. ✅ 多LLM服务商支持（Gemini、OpenAI、Claude、自定义服务商）
2. ✅ 本地向量数据库存储
3. ✅ 文档分片和向量化处理
4. ✅ 知识图谱生成与查询
5. ✅ 自然语言图谱结构设计功能
6. ✅ 任务状态跟踪（文档处理状态）
## 1. 后端编程语言和框架最终选型
### 选型结论：Python + FastAPI + LangChain
### 选型依据
| 需求点 | 技术适配说明 |
|--------|--------------|
| 多LLM服务商支持 | LangChain原生支持OpenAI、Anthropic、Google Gemini等主流服务商，同时支持自定义LLM封装，完美适配多服务商切换需求 |
| 文档分片和向量化 | LangChain提供完善的文档加载器、文本分割器、Embedding集成，大幅减少开发工作量 |
| 知识图谱生成 | Python拥有丰富的NLP库（spaCy、NLTK、LlamaIndex等），适合实体抽取、关系抽取等图谱生成任务 |
| 开发效率 | FastAPI自动生成API文档，类型提示完善，异步支持，适合快速迭代 |
### 架构分层设计
```
┌─────────────────────────────────────────┐
│               API 层                    │
│  FastAPI + Pydantic + 自动OpenAPI文档   │
├─────────────────────────────────────────┤
│               业务服务层                 │
│  文档服务 / 向量服务 / 图谱服务 / LLM服务│
│  任务服务 / 用户服务 / 权限服务          │
├─────────────────────────────────────────┤
│               核心能力层                 │
│  LangChain + LLM SDK + 知识抽取引擎      │
│  文档解析引擎 / 向量化引擎 / 图谱查询引擎│
├─────────────────────────────────────────┤
│               数据访问层                 │
│  SQLAlchemy + Redis + 向量数据库客户端   │
│  图数据库客户端                          │
└─────────────────────────────────────────┘
```
### 关键技术点
- **多LLM适配层**：基于LangChain的LLM抽象接口，开发统一的LLM调用SDK，支持动态切换服务商，统一接口格式
- **异步处理**：采用FastAPI异步路由 + asyncio，提升IO密集型任务（LLM调用、数据库查询）的并发处理能力
- **类型安全**：全链路使用Pydantic做数据校验，确保接口参数和内部数据结构的一致性
## 2. 数据库最终选型
### 2.1 关系型数据库：PostgreSQL 16+
**核心功能适配：**
- 存储用户信息、文档元数据、任务状态、图谱元数据等结构化信息
- 利用JSONB类型存储半结构化的文档分片内容、实体属性等数据
- 任务状态跟踪：使用PostgreSQL的事务特性保证任务状态更新的原子性，支持复杂的任务查询和统计
**表结构设计核心：**
```sql
-- 文档处理任务表
CREATE TABLE document_tasks (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id UUID REFERENCES users(id),
    file_name VARCHAR(255) NOT NULL,
    file_type VARCHAR(50) NOT NULL,
    file_size BIGINT NOT NULL,
    status VARCHAR(50) NOT NULL DEFAULT 'pending', -- pending/parsing/splitting/vectorizing/graphing/completed/failed
    progress INTEGER NOT NULL DEFAULT 0,
    error_message TEXT,
    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    metadata JSONB DEFAULT '{}'::JSONB
);
-- 文档分片表
CREATE TABLE document_chunks (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    document_id UUID REFERENCES document_tasks(id) ON DELETE CASCADE,
    content TEXT NOT NULL,
    chunk_index INTEGER NOT NULL,
    start_position INTEGER NOT NULL,
    end_position INTEGER NOT NULL,
    metadata JSONB DEFAULT '{}'::JSONB,
    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```
### 2.2 向量数据库：Qdrant（本地部署）
**选型依据（对比pgvector和Milvus）：**
| 特性 | Qdrant | pgvector | Milvus |
|------|--------|----------|--------|
| 本地部署支持 | ✅ 单节点部署简单，资源占用低 | ✅ 依赖PostgreSQL | ❌ 部署复杂，需要多个组件 |
| 向量检索性能 | ✅ 高性能，支持HNSW、量化等优化 | ⚠️ 千万级以上性能下降 | ✅ 超大规模性能优异 |
| 本地存储 | ✅ 数据存储在本地磁盘，完全可控 | ✅ 存储在PostgreSQL中 | ✅ 支持本地存储 |
| 功能丰富度 | ✅ 支持Payload过滤、多向量、分片 | ⚠️ 功能相对基础 | ✅ 功能最丰富 |
| 开发友好度 | ✅ HTTP/gRPC接口，Python SDK完善 | ✅ SQL查询，集成简单 | ⚠️ SDK相对复杂 |
**需求适配说明：**
- ✅ 本地部署：支持完全本地化部署，数据不出域，满足隐私安全要求
- ✅ 文档向量化：支持高效的向量插入、更新、删除，结合Payload过滤实现"文档ID + 向量"的混合检索
- ✅ 高性能查询：支持近似最近邻搜索，毫秒级返回查询结果
- ✅ 扩展性好：后期可平滑扩展为分布式集群
### 2.3 图数据库：Nebula Graph v3.6+
**选型依据（对比Neo4j和AGE）：**
| 特性 | Nebula Graph | Neo4j | PostgreSQL AGE |
|------|--------------|-------|----------------|
| 开源协议 | ✅ Apache 2.0，完全开源 | ⚠️ 核心功能开源，集群需要商业版 | ✅ PostgreSQL开源 |
| 分布式支持 | ✅ 原生分布式，水平扩展能力强 | ⚠️ 开源版不支持集群 | ❌ 单体架构 |
| 性能 | ✅ 超大规模图遍历性能优异 | ⚠️ 亿级以上性能下降 | ❌ 千万级以上性能瓶颈 |
| 数据模型 | ✅ 支持点、边、属性的灵活设计 | ✅ 灵活的属性图模型 | ✅ 属性图模型 |
| 查询语言 | ✅ nGQL，兼容OpenCypher | ✅ Cypher（事实标准） | ✅ OpenCypher |
**需求适配说明：**
- ✅ 知识图谱生成：支持高效的实体、关系插入，支持批量导入
- ✅ 图谱查询：支持复杂的图遍历、路径查询、子图查询，满足知识推理需求
- ✅ 自然语言图谱设计：支持灵活的Schema设计，可根据自然语言生成的结构动态创建点类型和边类型
- ✅ 扩展性：支持千亿级点边存储，满足未来业务增长需求
### 2.4 缓存与消息队列
- **缓存：Redis 7+**
  - 存储用户会话、热点查询结果、接口限流数据
  - 利用Redis Pub/Sub实现任务状态的实时推送
- **消息队列：RabbitMQ 3.12+**
  - 用于文档处理异步任务的分发和编排
  - 死信队列机制保证任务失败后的重试和告警
  - 相比Kafka更适合任务调度场景，消息可靠性更高，路由功能更灵活
## 3. 核心中间件和服务最终选型
### 3.1 文档解析服务：Unstructured.IO 0.12+
**需求适配：**
- 支持PDF、Word、PPT、Excel、TXT、Markdown、图片（OCR）等多种格式解析
- 结构化输出文档内容、标题、段落、表格、图片等元素
- 支持自定义解析规则，适配特殊格式文档
**部署方式：**
- 独立服务部署，通过HTTP API提供解析服务
- GPU加速版部署，提升OCR和复杂文档解析性能
### 3.2 文档分片与向量化处理
**技术栈：**
- **文本分片**：LangChain RecursiveCharacterTextSplitter + 自定义语义分片
  - 支持按字符数、token数、语义相似度等多种分片策略
  - 保留分片的上下文信息（所属文档、位置、标题层级等）
- **向量化引擎**：Sentence-Transformers + 多模型支持
  - 本地部署BGE-M3、gte-large等开源Embedding模型
  - 同时支持调用云端Embedding服务（OpenAI、通义千问等）
  - 支持向量维度可配置，适配不同业务场景需求
**处理流程：**
```
文档上传 → 格式校验 → 文档解析 → 文本清洗 → 语义分片 → 向量化 → 向量存储 → 知识抽取 → 图谱生成
```
### 3.3 多LLM服务商支持
**架构设计：**
```
┌─────────────────────────────────────────┐
│              统一LLM API                │
├─────────────────────────────────────────┤
│  LLM Provider 抽象层                    │
├───────┬───────┬────────┬────────────────┤
│OpenAI │Claude │Gemini  │ 自定义服务商    │
└───────┴───────┴────────┴────────────────┘
```
**核心特性：**
- 统一接口：所有LLM服务商实现相同的调用接口，上层业务无需关心具体实现
- 动态切换：支持运行时根据配置切换LLM服务商，支持按场景选择最优模型
- 降级机制：配置主备服务商，主服务不可用时自动切换到备用服务
- 成本控制：支持按模型价格、调用量进行成本统计和限流
- 自定义服务商：提供扩展接口，支持快速接入内部部署的开源大模型（如Qwen、Llama等）
### 3.4 知识图谱生成与查询
**技术栈：**
- **知识抽取**：基于大模型的Few-Shot抽取 + 规则引擎校验
  - 利用大模型从文档分片中抽取实体、属性、关系
  - 规则引擎对抽取结果进行校验和标准化，保证数据质量
- **图谱构建**：Nebula Graph Schema管理 + 批量导入
  - 支持动态Schema，根据自然语言设计的图谱结构自动创建点和边的类型
  - 批量数据导入工具，支持千万级实体/关系的高效导入
- **图谱查询**：nGQL查询封装 + 自然语言转查询接口
  - 封装常用的图谱查询接口（实体查询、关系查询、路径查询、子图查询）
  - 支持自然语言输入，自动转换为nGQL查询语句，降低使用门槛
### 3.5 自然语言图谱结构设计功能
**实现方案：**
1. **需求理解**：用户输入自然语言描述的图谱结构需求
2. **Schema生成**：大模型根据需求生成对应的图谱Schema（点类型、属性、边类型、关系约束）
3. **Schema校验**：系统对生成的Schema进行合法性校验，避免冲突和不合理设计
4. **Schema应用**：自动在Nebula Graph中创建对应的Schema结构
5. **示例生成**：自动生成示例数据和查询语句，帮助用户理解使用方式
**技术实现：**
- 采用Few-Shot Prompt工程，让大模型学习图谱Schema设计规范
- 开发Schema校验工具，确保生成的Schema符合Nebula Graph的最佳实践
- 提供可视化的Schema编辑界面，支持用户手动调整生成的Schema
### 3.6 任务状态跟踪
**实现方案：**
- **任务状态模型**：定义标准化的任务状态机
  ```
  pending → parsing → splitting → vectorizing → graphing → completed
               ↓          ↓           ↓           ↓
               →→→→→→→→→→ failed ←←←←←←←←←←←
  ```
- **进度跟踪**：每个处理阶段实时更新进度百分比，支持细粒度的进度展示
- **实时通知**：通过WebSocket + Redis Pub/Sub实现任务状态的实时推送
- **错误处理**：详细记录错误信息，支持任务重试和失败排查
- **任务管理**：支持任务列表查询、任务取消、任务优先级调整等功能

### 4.2 部署方式
#### 开发环境
- Docker Compose一键启动所有服务
- 支持热重载，提升开发效率
- 内置测试数据和Mock服务
#### 生产环境
- **小型部署（100用户以下）**：单服务器部署所有服务，配置16C/32G/2T SSD
- **中型部署（100-1000用户）**：
  - 应用服务器：2台8C/16G
  - 数据库服务器：PostgreSQL + Qdrant 4C/16G
  - Nebula Graph集群：3台4C/8G
  - 文档解析服务：1台8C/16G（带GPU）
- **大型部署（1000用户以上）**：
  - Kubernetes集群部署，所有服务容器化
  - 弹性扩缩容，根据负载自动调整资源
  - 高可用架构，所有组件多副本部署
### 4.3 监控与运维
- **日志收集**：ELK Stack统一收集所有服务日志
- **指标监控**：Prometheus + Grafana监控系统资源、服务状态、任务执行情况
- **链路追踪**：OpenTelemetry实现全链路请求追踪
- **告警系统**：Alertmanager实现异常告警，支持邮件、企业微信、短信等通知方式
## 5. 技术风险与应对方案
| 风险点 | 影响程度 | 应对方案 |
|--------|----------|----------|
| Nebula Graph学习成本高 | 中 | 1. 组织技术培训，重点学习nGQL和Schema设计<br>2. 封装常用查询接口，减少业务开发直接写nGQL的需求<br>3. 初期采用简单Schema设计，逐步优化 |
| 多LLM适配复杂度高 | 中 | 1. 基于LangChain抽象层开发，避免重复工作<br>2. 优先适配3个主流服务商，自定义服务商采用插件化扩展<br>3. 开发统一的测试套件，保证各服务商接口行为一致 |
| 文档解析准确率不稳定 | 高 | 1. 针对不同文档类型优化解析参数<br>2. 提供人工修正入口，允许用户调整解析结果<br>3. 建立bad case库，持续优化解析规则 |
| 向量检索准确率不足 | 中 | 1. 测试多种Embedding模型，选择最适合业务场景的模型<br>2. 优化分片策略，提高分片语义完整性<br>3. 支持混合检索（关键词 + 向量）提升准确率 |
