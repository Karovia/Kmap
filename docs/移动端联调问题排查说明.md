# Kmap 移动端联调问题排查说明

> 更新时间：2026-03-12
> 适用范围：Android / Capacitor 本地调试、局域网联调、前后端本机联调

## 1. 背景

在 `2026-03-12` 的真机验证中，移动端 App 出现了以下现象：

- 上传文件没有实际效果
- 添加服务商时点击“确认”只短暂显示 loading，然后没有响应
- 文档、图谱、设置页面统一提示：
  - `接口返回了非JSON内容，请检查前端代理或后端服务是否正常`

这些现象表面上像是“后端接口挂了”，但实际上是多个联调问题叠加导致的。

## 2. 现象总结

### 2.1 真机侧症状

- 文档页无法正确读取接口返回
- 图谱页无法加载概览数据
- 设置页无法获取或提交服务商配置
- 上传文件按钮可操作，但业务链路没有闭环

### 2.2 前端错误特征

- 前端统一抛出：
  - `接口返回了非 JSON 内容，请检查前端代理或后端服务是否正常`

这通常意味着：

- 请求并没有打到真正的后端 JSON API
- 或者打到了错误地址，拿到了 HTML / 空响应 / 非 JSON 响应

## 3. 根因分析

## 3.1 Android App 不能依赖 Vite 代理

Web 开发阶段，前端请求 `/api/...` 时会经过 `vite.config.ts` 中的 dev proxy 转发到本地后端。

但打包后的 Android / Capacitor App 不在 Vite dev server 环境里运行，因此：

- 相对路径 `/api/...` 不会自动代理
- App 很可能拿到本地静态页面 HTML
- 前端 JSON 解析失败，于是出现“非 JSON 内容”的统一报错

这是本次问题的**第一根因**。

## 3.2 本机 `8000` 端口被其他进程占用

联调时发现本机 `8000` 端口被 `com.docker.backend` 占用，因此即使本地后端默认配置为 `8000`：

- 也可能无法成功绑定
- 或者前端代理与移动端配置会误连到错误服务

因此本次联调改用 `8001` 作为后端本地调试端口。

## 3.3 后端依赖服务未启动

当前后端并不是“单进程即可完整运行”的结构，还依赖：

- PostgreSQL
- Redis
- RabbitMQ
- Qdrant
- （图谱相关时）Nebula Graph

即使前端 API 地址修对了：

- 如果这些基础服务没起来
- 文档、服务商、图谱、异步处理链路仍然可能失败

这也是为什么“地址问题修完”后，仍然需要继续检查后端运行环境。

## 3.4 Gemini 依赖是按需能力，不是启动阻塞项

后端代码已经接入 Gemini provider 路径，但本地环境未必安装了 `google-generativeai`。

目前的处理策略是：

- 后端服务允许先启动
- 只有真正调用 Gemini 时才提示缺失依赖

因此 Gemini 问题不是这次“非 JSON 返回”的主因，但会影响服务商联调结果。

## 4. 已完成修复

## 4.1 统一前端 API 基址解析

新增统一 API 地址解析层：

- `src/services/apiBase.ts`

核心逻辑：

- Web 开发时仍可使用相对路径和 Vite 代理
- Android / Capacitor 环境优先使用 `VITE_API_BASE_URL`
- 避免打包后的 App 继续依赖 `/api` 相对路径代理

## 4.2 统一服务层请求入口

已把文档和服务商相关请求切到统一 API 地址逻辑：

- `src/services/httpClient.ts`
- `src/services/documentsService.ts`
- `src/services/providersService.ts`

这样上传、删除、服务商测试等原本直接 `fetch('/api/...')` 的逻辑，不再依赖浏览器代理。

## 4.3 允许本地替换后端调试端口

已支持通过以下变量指定联调地址：

```bash
VITE_API_BASE_URL=http://你的局域网IP:8001
VITE_API_PROXY_TARGET=http://127.0.0.1:8001
```

对应修改位置：

- `vite.config.ts`
- `.env.example`

## 4.4 增加 Windows 一键启动脚本

已增加以下脚本：

- `scripts/start-frontend-dev.cmd`
- `scripts/start-backend-dev.cmd`
- `scripts/start-dev-services.cmd`

这些脚本的目标是减少本地手工敲命令的成本，便于 Windows 环境快速联调。

## 4.5 已重新构建 Android 预览包

已重新生成：

- `android/app/build/outputs/apk/release/Kmap-P1-preview.apk`

该包基于当前联调配置重新打入了前端资源，适合继续用于真机验证。

## 5. 当前联调口径

本次联调建议统一使用：

- 前端 Dev：`3000`
- 后端 Dev：`8001`
- Android / 真机 API 地址：电脑当前局域网 IP + `8001`

本次排查时观察到电脑 WLAN 地址为：

```text
10.157.64.171
```

因此本次本地联调示例值为：

```bash
VITE_API_BASE_URL=http://10.157.64.171:8001
VITE_API_PROXY_TARGET=http://127.0.0.1:8001
```

注意：

- 这个 IP 只对当前网络环境有效
- 换网络、换热点、换 Wi-Fi 后需要重新确认

## 6. 仍未彻底解决的部分

### 6.1 后端长驻进程稳定性

当前 CLI / 本地终端环境下，后端后台常驻方式还不够稳定；前台可启动，不代表后台一定能稳定驻留。

因此在手工联调时，建议：

- 明确确认后端端口真的在监听
- 通过健康检查验证服务真实在线

### 6.2 后端基础依赖服务

即使后端 API 进程启动成功，若以下服务没有正常运行，功能仍可能失败：

- PostgreSQL
- Redis
- RabbitMQ
- Qdrant
- Nebula Graph（部分图谱能力）

其中最直接影响当前真机测试的是：

- 文档列表 / 服务商配置依赖数据库
- 文档上传处理依赖消息队列和向量库

### 6.3 Windows 防火墙与局域网访问

真机能否访问电脑上的后端，还取决于：

- 手机与电脑是否在同一局域网
- Windows 防火墙是否放行 `8001`
- 企业网络 / 校园网是否屏蔽局域网互访

## 7. 推荐验证顺序

### 第一步：确认后端在线

在电脑浏览器中访问：

```text
http://127.0.0.1:8001/api/v1/health
```

如果这里都不通，手机端一定也不通。

### 第二步：确认手机能访问电脑

在手机浏览器中访问：

```text
http://10.157.64.171:8001/api/v1/health
```

如果手机浏览器都打不开：

- 优先检查局域网
- 再检查防火墙
- 最后检查后端端口是否真的启动成功

### 第三步：重新安装新的 APK

重新安装：

- `android/app/build/outputs/apk/release/Kmap-P1-preview.apk`

避免继续验证旧包。

### 第四步：验证页面接口

建议顺序：

1. 设置页
   - 先看服务商列表是否能打开
2. 图谱页
   - 再看概览接口是否能返回
3. 文档页
   - 最后验证上传、删除和状态轮询

这样更容易快速判断：

- 是“所有 API 都不通”
- 还是“后端在线但个别业务依赖没起来”

## 8. 结论

本次移动端联调问题的核心不是单一 bug，而是以下三类问题叠加：

1. 打包后的 Android App 错误地依赖了 Vite 代理
2. 本机 `8000` 端口被其他进程占用
3. 后端及其依赖服务未完整启动

已完成的修复重点在于：

- 把前端 API 访问从“相对路径代理”改成“可配置的真实后端地址”
- 为 `8001` 调试端口和局域网联调留出明确入口
- 重新构建了新的 Android 预览包

后续工作的重点则应放在：

- 确保后端真实在线
- 拉起 PostgreSQL / Redis / RabbitMQ / Qdrant 等依赖
- 再进行真机业务链路验证
